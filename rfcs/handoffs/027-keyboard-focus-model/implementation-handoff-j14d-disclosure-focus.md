## The defect (your finding 2, confirmed against snora's source)

After **Space on the "Advanced settings" header** the focus ring is gone: nothing is focused and the next Tab starts at the first navigation item, a dozen stops away. The same must happen with the **Preview toggle** on the Result screen (it adds the preview's controls). Cause, from `snora-interaction-0.65.0/src/inert.rs` ("After a removal"): after a press, snora's `Inert` surveys the focus targets; if the count of targets has changed and the control did not declare a removal (`Control::removes`), **nothing is focused**; and, as I read it, **a focus the application sets on the pressed control's own position is treated as "inherited" and taken off** (the application's choice wins only if focus is anywhere *but* the pressed control's position). snora's documented rule is deliberate for removals; it does not describe a control that *adds* stops after itself, which is what a disclosure does. A keyboard user expects the focus to stay on the header (WCAG 3.2.2, predictable). Two buttons are affected: the "Advanced settings" header and the Preview toggle. (Enter on a navigation item changes the page; focus nowhere there is accepted and documented.)

## Time box and decision rule

One short working session. **Step 1 — find out (no commit):** reproduce headless with the J14a/J14b session driver: Tab to the header, Space: where is the focus after the rebuild? Then try, in order, and **report what each does with evidence**:
 1. The application focuses the header by `Id` (`snora::control(...).id(id)`, `iced::widget::operation::focus(id)`) in the same `update` that toggles it. Does Inert take it off (my reading), or keep it?
 2. The same focus task issued one message later (a follow-up message produced after the redraw; **no timer**, a message round trip only), so it runs after Inert's observation. Is the order deterministic in the real runtime (read iced's event loop: redraw versus message processing) or does it depend on timing? If it depends on timing, it is not acceptable.
 3. Anything else you find in snora's API that declares "this control keeps focus when stops are added after it" (read `Control` and `Inert` fully; report the exact names).
**Step 2 — decide with this rule:** if (1) or (2) gives a **deterministic, timer-free, headless-testable** way for the header and the Preview toggle: implement it (smallest change; a shared helper for both; tests: after Space the same control is focused, its ring is drawn, the page scrolled it into view; after Space again (closing) it is still focused; Enter does the same; the Tab order after is the layout order from there). If **neither** works deterministically: **stop; change no code**, and report the exact reason; the architect then sends snora a request (a draft is ready) and lists the behaviour as a known limitation.
**Either way** the last commit updates `docs/release-notes/1.28.0.md` (if it is a limitation: one bullet under Known limitations: "Opening the Advanced settings or the Preview section with the keyboard leaves no control focused; press Tab to continue from the top"; if it is fixed: nothing) and `docs/src/ui-a11y.md` "Known behaviour" to match.
