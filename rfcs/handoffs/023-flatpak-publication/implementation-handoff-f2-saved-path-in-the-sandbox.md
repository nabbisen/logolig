# Developer Handoff — Flathub sandbox findings, job F2: the saved-file message must not show a portal path

Role and rules as always (commits on `main`, gates chained with `&&` and their exit status tested before commit and push, `git log origin/main..` before every push, wait for CI on each commit, relative `cd`). No version change, no tag, no release.

## The defect (found by the owner in a real Flatpak run, 2026-11-26)
After saving ("Download" one file, or "Download all (ZIP)"), the success message shows the path **as the file chooser returned it**. Inside a Flatpak the chooser is the portal, and the path it returns is a document-portal path: `/run/user/<uid>/doc/<document id>/<file name>`. The file is saved where the user chose, but that path means nothing to the user (it is not in their home directory, and it does not exist outside the sandbox). A message that names a place the user cannot find misleads, and "no confusing or misleading UI" is the owner's rule.

The code (`crates/app/src/app/update/download.rs`, `download_one_completed` and `download_all_completed`): `let body = format!("{}", path.display());`.

## Decision (mine; the owner can overrule)
**Show only the file name when the path is a document-portal path; otherwise show the full path exactly as today.** Why the file name and not the real folder: the real host folder is not known to the sandboxed process without asking the Documents portal again (a feature of `ashpd`, a new surface and a portal version dependency). The user has just chosen the folder in the chooser, so the name alone is true and enough. **Out of scope and parked:** asking the portal for the host path. No new package, no new feature, no `unsafe`, no `#[allow]`.

## Work
1. **Find every place the application shows a file path to the user** (grep `display()`, toasts, error messages that carry a path; the technical details inside `AppError` strings in `task_queue.rs` are for the log and are not "shown" unless a view renders them: check which ones a view renders, and report the list). Fix only what the user can see. Report anything else you find; do not widen the job.
2. **A lateral sweep for the same class of defect: "a path or an environment fact that is true outside the sandbox and false inside it"** (owner's request, 2026-11-26). My survey, which you verify (correct me where it is wrong; do not take it on trust): (a) the application only ever writes **one file at the exact path the chooser returned** (`std::fs::write` in `write_one_task` and `write_zip_blocking`); it creates **no sibling or temp file and no directory** (`exporter::run_in_memory` is the only exporter call; the staged-directory `exporter::run` is not used by the app), which is what a document-portal path allows; (b) user-visible file names come from `file_name()` (`SourceAsset::display_name`, the write-error text of RFC 014 D4), never a full path: the success toast is the one outlier I found; (c) no path is persisted (`PersistedSettings` holds the export plan, theme, locale and interface size); (d) the environment is read in `portal.rs` only (`/.flatpak-info`, `SNAP`, `PATH`, the session bus). **Write the sweep as a short list in your report**: every place that (1) shows a path, (2) stores a path, (3) writes next to or around a user-chosen path, (4) reads `HOME`, `XDG_*`, the current directory or `/proc`, `/sys`, `/etc`, `/usr`, (5) starts a program or opens a URL or folder, (6) derives something from a **dropped or chosen source path** (a dropped file also arrives as a document-portal path inside Flatpak: check that nothing but the file name and the content is used). For each: "not affected", or "affected: fixed in this job" (only if it is a displayed path), or "affected: reported, not fixed". Facts that **only a real sandbox run can show** (fonts for Japanese, system theme following, locale at launch, the window icon and name, drag-and-drop from the file manager, the settings location) are the owner's run, not yours: list them as "not verified here".
3. **One small pure function** (in the app crate, with the other path helpers or next to `download.rs`; your choice, reported): `path_for_message(path: &Path, runtime_dir: Option<&Path>) -> String`, which returns the file name when `path` lies under `<runtime_dir>/doc/` and the full `path.display()` otherwise. `runtime_dir` is `XDG_RUNTIME_DIR` read by the caller (the function itself reads no environment, so it is testable). If `XDG_RUNTIME_DIR` is unset or empty, fall back to the literal prefix `/run/user/<digits>/doc/`. A path without a file name (cannot happen from the chooser) falls back to the full path. Linux logic only; on Windows and macOS the function returns the full path unchanged and a test says so (`cfg` as the code base already does it, no `#[allow]`).
4. **Use it in both completed-handlers** (and in any other place item 1 finds).
5. **Docs:** one sentence in `docs/src/functional-spec.md` where the success message is described (or the nearest place that says what it shows): the file name inside Flatpak, the full path elsewhere.
