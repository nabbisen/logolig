## Part 0 — the proposal (no code; stop and report)

Write the proposal as one table in the review request (and in `.git-exclude/tmp/ja-review-1.29.0.md`, appended, for the owner), **for every user-visible string of the Customize page and its Advanced block**: the key, the **current English and Japanese**, the **proposed English and Japanese**, and a one-line reason. Source: `crates/i18n/locales/{en,ja}.toml` (the keys around `section_png_output_sizes`, `section_svg_conversion`, `keep_transparency`, `advanced_*`, `algorithm_*`, `vtracer_preset_*`, `section_svg*`, `include_*`, `section_web_manifest*`, `section_monochrome*`, `section_microsoft_app_logos*`, the manifest field labels, the custom-size placeholder). **Rules (binding):**
1. **Say what the option gives the user, in the user's words.** Example direction only (you propose the real text): "apple-touch-icon.png (iOS / iPadOS home screen)" → "Icon for iPhone and iPad home screens (apple-touch-icon.png)"; "Vectorize raster sources to SVG (vtracer)" → "Turn a PNG or JPEG into a scalable SVG"; "Output mono/ grayscale set" → "Also make black-and-white versions". **The file name or technical term stays, as a secondary part of the same line or in the blurb**, because a web developer looks for `favicon.svg` by name and the output files keep their names.
2. **Each resize algorithm and each tracing preset gets one plain line** saying when to choose it ("Lanczos3 (sharp)" → "Sharpest for most logos (Lanczos3)"; "Nearest (pixel art)" → "Keeps hard pixel edges, for pixel art (Nearest)"), the technical name in brackets after the plain part. **Keep the defaults visibly marked** ("recommended") only if it is true to the code (`ResizeAlgorithm::default`, `VtracerPreset::default`).
3. **Explain `favicon`, `ICO`, `apple-touch-icon` once**, in the blurb under the first section that needs it ("A favicon is the small icon in a browser tab…"), not on every row. **No jargon in a title**; jargon only in brackets or a blurb.
4. **Section order and presence do not change in this job** (less is more; moving things is a design decision for another day): only the texts. If you believe an order change is needed, say so as a *question* in the proposal, do not do it.
5. **Length:** a label fits one line at 16 px at 360 px wide in Japanese **or wraps cleanly**; blurbs are at most two short sentences. The J22 matrix will tell you; propose nothing the matrix cannot hold without a layout change.
6. **Nothing the program does not do** (RFC 018's lesson): do not promise "works on every device"; the ICO frame sizes are fixed (16, 32, 48) and not editable: do not say "all sizes"; SVG text is not drawn.
7. **Japanese is written by you as natural Japanese for a layperson, not translated word by word**, in the file's existing style (です/ます; parentheses as half-width as in the neighbouring strings; the half-width space habit after 、 and 。 is **the owner's open question**: follow the file as it is now, do not sweep). The owner reads the list; **it is not blocking** (if the owner has not reviewed it by the release, the notes say so again).
8. Keep the **keys**; add keys only where a new sentence is needed (a blurb, a "recommended" tag); a key that becomes unused is **deprecated, not removed** (the public `MessageKey` rule, the existing `allow(deprecated)` pattern).

**Stop here and report** (review request `.git-exclude/review-request/rfc-034-j23-plain-language/README.md`, report only its path). The architect reviews the proposal (and asks the owner about the Japanese if useful), then confirms the build. Do not change any file under `crates/` in this part.

## Architect's decisions on the Part 0 proposal (2026-11-24): Part 1 may start

Reviewed in `.git-exclude/reviewed/rfc-034-j23-proposal-review-2026-11-24.md`. The proposal is **accepted as written except for these five changes (binding)** and the answers below:

1. **`section_misc` is not "Background".** The manifest block has a field "Background color"; a section named "Background" would collide with it. Title: **"Transparent areas"** (JA **透明な部分**). The option label: **"Keep transparent areas (alpha)"** (JA **透明な部分をそのまま残す (アルファ)**); its blurb (white fill when off, SVG unchanged: verified by me against `flatten.rs`, "fixed at white") stays.
2. **The SVG-conversion blurb must state the dependency**, not only "these choices apply when a PNG, WebP or JPEG is turned into SVG": add that this happens only when the option **"Turn a PNG, WebP or JPEG into SVG" under Advanced settings** is on (say "it is on by default" **only if** `ExportPlan::default().vectorize_on_raster` is true: check and test it; it reads `true` at `export_plan.rs:140`). Two sentences at most. The group's position does not change.
3. **Algorithm lines: no claim without evidence.** In Part 1, **measure** each algorithm on one synthetic hard black/white edge scaled to 32 px (and 16 px): the edge's transition width (10–90 %) and the overshoot (halo) as numbers, plus a small CPU-only picture of the four results side by side for my eyes, kept in the review request. The words "crisp", "softer", "fewer halos", "faint halos" must **follow the numbers** (rank them); **drop "a close second choice" and "simple"** (opinions the program cannot support). Keep "recommended" on `Lanczos3` and `Default` only, each pinned by a test against `::default()`.
4. **Japanese for grayscale is グレースケール**, the word a layperson already knows from photo apps (section title **グレースケール版**, label **グレースケール版も出力 (mono フォルダー)**); English stays "Grayscale copies" / "Also save grayscale copies (in the mono folder)". Not "グレーの濃淡の版".
5. **ICO:** "(ICO is the classic favicon.ico file format)", not "older".
