## What the source says (architect's reading; confirm each in your report)

- iced `application(...).scale_factor(|state| f32)` (`iced-0.14.0/src/application.rs`, `with_scale_factor`) multiplies the system's scale: the window state's viewport scale is `window.scale_factor() × scale_factor` (`iced_winit-0.14.0/src/window/state.rs`), so **everything** (text, icons, paddings, fixed widths) grows together and **`window::Event::Resized` reports the logical size of that scaled viewport** (`viewport.logical_size()`): at 150 % a 1280 × 720 window is 853 × 480 logical. `AppState::window_size`, which the mobile breakpoint reads (`MOBILE_BREAKPOINT_PX` 768), is therefore **already in scaled pixels**: no extra code for D2's last point; prove it (below).
- `window::set_min_size(id, Some(size))` converts the **logical** size with the **same combined scale** (`iced_winit` `Action::SetMinSize`: `.to_physical(window.state.scale_factor())`), at the time of the call. So a minimum window size expressed in logical pixels is correct at any step **if it is re-issued after the step changes**.
- A layout depends only on the logical window size. **The existing headless matrix therefore already covers every step**, provided the window never gets smaller than the matrix floor in logical pixels (**360 × 480**, the smallest size of the matrix). Today the application sets **no minimum window size**, so a user could shrink the window below what is tested; with a 150 % step the floor is 540 × 720 physical.
