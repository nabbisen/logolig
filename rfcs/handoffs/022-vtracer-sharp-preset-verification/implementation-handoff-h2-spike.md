## Why it matters now (not only housekeeping)

Since J23 the Customize page says **"Logos and icons, with crisp edges (Sharp)"** (JA ロゴやアイコン向け・輪郭くっきり). The only difference of `Sharp` from vtracer's defaults is `corner_threshold: 80` (default 60; `PhotoRich` 45). By vtracer's own definition `corner_threshold` is the **minimum** momentary angle to count as a corner: a *higher* minimum means *fewer* joints are corners, so **more** of the outline is smoothed: 80 would be *rounder*, not crisper, than 60. If that is true, **a sentence in our user interface is false.** The default (`VtracerPreset::Default`) is unaffected; only users who choose "Sharp" are.

## Questions and method (objective numbers, a few pictures)

1. **Q1 What does each `corner_threshold` do to a known shape?** Fixtures (in the scratchpad, with sha256 recorded; none committed): (a) a **square** (and a rotated square) with hard corners, (b) a **hexagon**, (c) a **letter-like polygon** with sharp and obtuse corners, (d) a **circle** (control: no corners), (e) a **gradient/photo-like** image (control for PhotoRich). Trace each through the **same code path the application uses** (`logolig::services::vectorize` or whatever `config_for(VtracerPreset)` feeds; read `crates/core/src/services/` and call `config_for` for `Sharp`, `Default`, `PhotoRich`) **and additionally** with `corner_threshold` 30, 45, 60, 80, 100 and everything else default (Spline mode as the application uses it).
2. **Metric (a number, not an impression).** For the traced SVG, parse the path data and measure at each **true corner** of the fixture (known coordinates): the **corner rounding** = the distance from the true corner point to the nearest point of the traced outline (0 = a sharp corner kept; larger = cut or rounded), in pixels of the source, and the **number of path nodes** and the SVG size in bytes. Report a table per fixture × threshold. A short script (Python with `-I`, or a Rust example) is fine; keep it in the review request folder.
3. **Q2 Pictures for the architect's eyes** (small): the square and the hexagon at 16, 64 and 512 px for `Sharp`, `Default`, `PhotoRich`, rendered from the SVG; one sheet.
4. **Q3 How do the user-facing words map?** Read where the UI maps the three presets (`ui/advanced_drawer/choices.rs` / the SVG group) and the strings: the label of each preset (en.toml/ja.toml, as of J23) and the core doc comments of `VtracerPreset`. Say which claims are **supported by Q1/Q2 numbers** and which are not ("Logos and icons, with crisp edges", "A balance for most pictures", "Photos and gradients, keeps fine color differences").
5. **Q4 vtracer's own documentation:** quote the exact sentences of the `corner_threshold` doc in the vendored source (`~/.cargo/registry/src/*/vtracer-*/`), and of the sibling parameters (`filter_speckle`, `color_precision`, `layer_difference`, `length_threshold`, `splice_threshold`, `path_precision`) that `config_for` sets for each preset, so that a recommendation can use them.

## Recommendation (do not implement)

Decide with the numbers one of: **(a) keep** the preset (the numbers show 80 keeps corners at least as well as 60) and the label stands; **(b) change the value** (for example 60 → or lower for `Sharp`; say which value gives the best corner preservation on (a)–(c) without more nodes than a stated factor, with the table) and note that this **changes the SVG output** for users who chose Sharp (a behaviour change needing the architect's decision, golden tests and a line in the release notes); **(c) keep the value and change the words** so that name and effect agree (give the proposed English and Japanese; a change of words is the architect's and the owner's decision). Also say whether `PhotoRich` (45) and `Default` (60) behave as their labels claim.
