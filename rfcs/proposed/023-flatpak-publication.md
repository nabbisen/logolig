# RFC 023 — Flatpak publication (Flathub)

**Status.** Proposed
**Priority.** P2 (after the first AUR release; shares prerequisites with RFC 020)
**Tracks.** Distribution to a broader range of Linux users.
**Touches.** `packaging/linux/` (desktop file, AppStream metainfo, icon), `packaging/flatpak/` (owner-authored manifest, see "AI policy"), `.github/workflows/` (validation job), window application id (RFC 025), docs.

## Summary

Publish Logolig on Flathub, which reaches users of every distribution and runs the application in a sandbox. The project's product promise (offline, local-first) maps directly onto Flatpak permissions: the application needs **no network permission and no filesystem permission**, a claim users can verify. Flathub builds the application itself from source, so "via GitHub" means: the source and the validation CI live in this repository; the Flathub package is a pull request to `flathub/flathub` and then a repository under the Flathub organisation.

## Evidence

Requirements verified by fetching the Flathub documentation on 2026-10-21 (`docs.flathub.org`, "Requirements" and "Submission"). **The owner should read both pages directly before submitting**; this RFC summarises, and the policies change.

- **App ID.** GitHub-hosted apps use `io.github.<user>.<App>`, at least four components, repository derived from the ID and reachable; the ID must equal `<id>` in the MetaInfo file and must not end in a generic term. Candidate: `io.github.nabbisen.Logolig` (repository is `nabbisen/logolig`; GitHub URLs are case-insensitive, to be confirmed with the reviewers).
- **Build has no network access** (`--share=network` in `build-args` does not work). Dependencies must be listed as sources; manifests generated by tools (cargo) must be included. Binaries and prebuilt artefacts are not allowed.
- **Portals are mandatory where a suitable portal exists** instead of static permissions; permissions must be minimal. Verified locally: the application's `rfd 0.15.4` uses the XDG portal backend by default, so file chooser and save dialogs already go through the portal.
- **Icon:** SVG preferred, otherwise at least 256 × 256 PNG. MetaInfo must validate and carry the licence; a desktop file is mandatory; complete English localisation.
- **Manifest** at the top level of the submission, named after the app ID; the runtime must be on Flathub and current; single-architecture apps need `flathub.json`.
- **AI policy (important).** AI-generated or AI-assisted content is **not allowed in manifests**; other AI-generated material must be disclosed; AI tools **must not open or automate submission PRs, or write their descriptions, commit messages or review replies**.
- **Process.** PR against the `new-pr` branch of `flathub/flathub`; test builds by commenting `bot, build`; reviewers may ask for changes; approved apps get their own repository (2FA required); official builds follow after merge; updates are PRs to that repository.

Local facts (verified by execution unless stated):

- The application reports an **empty Wayland `app_id`** (`niri msg windows`), so a desktop entry cannot be matched to the window (RFC 025).
- No `.desktop` file, MetaInfo file or Linux icon exists in the repository; a master icon is not available (RFC 020 D5). `docs/assets/screenshot-01.png` (1026 × 943) exists.
- Settings are stored through `app-json-settings` in the user's config directory; Flatpak redirects `XDG_CONFIG_HOME`; to be confirmed.
- The locked dependencies need Rust 1.90 (RFC 024); a current Flatpak SDK extension provides a recent stable Rust (to be confirmed at build time).
- Not verified: wgpu/iced rendering inside the sandbox (GPU access, fallback renderer), font visibility inside the sandbox (matters for SVG text, RFC 015 phase 2b, because fontdb scans default directories and the sandbox exposes a different font set).

## Options for "via GitHub"

| Option | What | Assessment |
|---|---|---|
| A (recommended) | Flathub: `flathub/flathub` PR, then a Flathub-hosted repository; our repository keeps the upstream files and a validation job | Largest reach, automatic updates for users, review adds quality control; costs: human-only submission, Flathub review, no network at build |
| B | CI builds a `.flatpak` bundle and attaches it to each GitHub release | Easy, but users install by hand and get no updates; useful as a test artefact, not as a channel |
| C | Own Flatpak repository served from GitHub Pages | Full control and updates, but users must add a remote and trust it; extra signing/key operations (security burden) |

## Proposal

1. **Shared upstream files** (also used by the AUR package, RFC 020): desktop file, MetaInfo, icon, window app id. Use the reverse-DNS ID `io.github.nabbisen.Logolig` as file names (`io.github.nabbisen.Logolig.desktop`, `.metainfo.xml`, icon name) so that one set of files serves both packages (decision D4; this changes the file names currently planned in the RFC 020 phase-2 handoff, which has not been started).
2. **MetaInfo** (upstream, validated by `appstreamcli validate`): `<id>`, name, short summary, description, `project_license` Apache-2.0, `metadata_license` CC0-1.0, screenshots (stable public URLs), releases, content rating, categories, URLs. Texts follow the project rule "less is more".
3. **Sandbox permissions (proposal):** `--socket=wayland`, `--socket=fallback-x11`, `--share=ipc` (only with X11), `--device=dri`. **No** `--share=network`, **no** `--filesystem=*`. File access exclusively through portals. Any addition needs an RFC amendment.
4. **Manifest:** authored by the **owner**, not by an AI agent, and kept in `packaging/flatpak/` so it is reviewed in this repository; the cargo source list is generated with Flathub's `flatpak-cargo-generator`. Build with `--offline`, `--locked`, release profile.
5. **CI (first-party only where possible):** a job that validates the desktop file and MetaInfo and builds the manifest with `flatpak-builder`, then runs `flatpak-builder-lint` against the manifest and the repo. The tooling container image is a third-party image: pin by digest and record the decision.
6. **Submission and maintenance by the owner**: open the Flathub PR by hand, answer reviewers by hand, and update by pull request after each release. A bot for source updates (Flathub's external-data checker) is acceptable only if the owner confirms it is not covered by the AI restriction.

## AI policy: how the project handles it (decision D3)

The project is developed with AI agents. For Flathub: the manifest and the submission (PR text, commit messages, review replies) are written and sent by the owner without AI assistance; AI-produced upstream files (MetaInfo, desktop file, code) are disclosed in the submission as the policy requires. The owner should check the policy text on the day of submission and, if in doubt, ask the Flathub reviewers first. **Risk:** a reviewer may object to AI-assisted source in general; the decision to proceed, and what to disclose, is the owner's. Agents prepare everything upstream and the evidence; they do not touch the Flathub repository or PR.

## Phases

0. Owner decisions D1–D6; RFC 025 (app id) and RFC 024 (MSRV) done; master icon (RFC 020 D5).
1. Upstream files and validation CI; local build and run of the Flatpak by the owner; evidence for GPU, fonts, file dialogs and settings inside the sandbox.
2. Owner submission to Flathub.
3. Maintenance per release.

## Decisions requested

- **D3** The AI-policy handling above, including disclosure.
- **D4** Use the reverse-DNS ID for the desktop file, MetaInfo and icon names for both AUR and Flatpak (amends the RFC 020 phase-2 handoff before it starts).

## Tests and evidence

Validation commands in CI; local runs recorded: `appstreamcli validate`, `desktop-file-validate`, `flatpak-builder-lint`; a run of the built Flatpak with the owner's real session (Wayland and X11): window opens, file chooser via portal, ZIP save, settings persisted under `~/.var/app/<id>/`, no network access attempted (verify with `flatpak run --no-network` or an equivalent check).

## Acceptance criteria

The Flatpak builds offline from the manifest, validates cleanly, runs with the permission set above, and the Flathub submission is open or merged; documentation (`README.md` install section) is updated only after the package exists.

## Risks

| Risk | Rating | Mitigation |
|---|---|---|
| Flathub rejects AI-assisted source | Medium | Owner checks the policy first; disclose; ask reviewers early |
| Renderer does not start in the sandbox | Medium | Phase 1 evidence before any submission; document fallback |
| SVG text differs inside the sandbox | Medium | RFC 015 phase 2b evidence includes the Flatpak font set |
| Review latency and maintenance burden | Low-Medium | One maintainer; keep permissions minimal; automate validation |
